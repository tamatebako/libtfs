= ZIP Backend Documentation
:toc:
:toclevels: 3

== Overview

The ZIP backend provides read-only access to ZIP archives through the unified [`FileSystem`](../../include/tebako/fs/filesystem.h) interface using libzip.

== Architecture

The ZIP backend consists of three main classes that implement the VFS abstraction layer.

=== ZipBackend

Main backend class implementing the [`FileSystem`](../../include/tebako/fs/filesystem.h) interface.

.Class Declaration
[source,cpp]
----
class ZipBackend : public FileSystem {
 public:
  ZipBackend();
  ~ZipBackend() override;

  // Lifecycle methods
  bool mount(const std::string& archive_path,
             const std::string& mount_point) override;
  void unmount() override;
  bool is_mounted() const override;

  // File operations
  std::unique_ptr<FileHandle> open(const std::string& path,
                                    int flags) override;
  bool exists(const std::string& path) const override;
  bool is_file(const std::string& path) const override;
  bool is_directory(const std::string& path) const override;

  // Directory operations
  std::unique_ptr<DirectoryIterator> list_directory(
      const std::string& path) override;

  // Metadata operations
  int64_t file_size(const std::string& path) const override;
  time_t modification_time(const std::string& path) const override;
  mode_t permissions(const std::string& path) const override;

  // Backend info
  std::string backend_name() const override;
  std::string backend_version() const override;
  std::string archive_path() const override;
  std::string mount_point() const override;
};
----

.Key Responsibilities
* Archive mounting and lifecycle management
* Path resolution and translation
* Thread-safe access to libzip handle
* Resource cleanup on unmount

=== ZipFileHandle

Implements [`FileHandle`](../../include/tebako/fs/file_handle.h) for reading files from ZIP archives.

.Features
* Sequential reading with buffering
* Position tracking ([`tell()`](../../include/tebako/fs/file_handle.h:45))
* EOF detection ([`eof()`](../../include/tebako/fs/file_handle.h:52))
* Seek support via close/reopen pattern
* Thread-safe file operations

.Seek Implementation
ZIP format does not support native seeking. The implementation uses a close/reopen strategy:

[source,cpp]
----
off_t ZipFileHandle::seek(off_t offset, int whence) {
  // Calculate target position
  off_t target = calculate_target_position(offset, whence);

  // Close current file
  zip_fclose(zf_);

  // Reopen at beginning
  zf_ = zip_fopen_index(archive_, index_, 0);

  // Read and discard bytes until target position
  skip_to_position(target);

  return position_;
}
----

This approach has a 5-20 ms overhead but maintains compatibility with the [`FileHandle`](../../include/tebako/fs/file_handle.h) interface.

=== ZipDirectoryIterator

Implements [`DirectoryIterator`](../../include/tebako/fs/directory_iterator.h) for traversing directories.

.Capabilities
* Iterates entries at a specific directory level
* Filters entries by directory prefix
* Provides entry metadata ([`DirectoryEntry`](../../include/tebako/fs/directory_iterator.h:42) structure)
* Supports reset for re-iteration

== Usage Examples

=== Basic File Reading

[source,cpp]
----
#include <tebako/fs/backend_factory.h>

using namespace tebako::fs;

// Create backend
auto backend = BackendFactory::create_zip();

// Mount archive
if (backend->mount("archive.zip", "/mnt/app")) {
  // Open file
  auto handle = backend->open("/mnt/app/file.txt", O_RDONLY);
  if (handle) {
    // Read content
    char buffer[1024];
    ssize_t bytes = handle->read(buffer, sizeof(buffer));

    // Process data
    std::cout.write(buffer, bytes);
  }

  // Unmount when done
  backend->unmount();
}
----

=== Directory Traversal

[source,cpp]
----
auto backend = BackendFactory::create_zip();
if (backend->mount("archive.zip", "/mnt/app")) {
  // List directory
  auto iter = backend->list_directory("/mnt/app/docs");

  while (iter && iter->has_next()) {
    auto entry = iter->next();

    std::cout << entry.name;
    if (entry.is_directory) {
      std::cout << " (directory)";
    } else {
      std::cout << " (" << entry.size << " bytes)";
    }
    std::cout << std::endl;
  }

  backend->unmount();
}
----

=== File Metadata

[source,cpp]
----
auto backend = BackendFactory::create_zip();
if (backend->mount("archive.zip", "/mnt/app")) {
  std::string path = "/mnt/app/document.pdf";

  // Check existence
  if (backend->exists(path)) {
    // Get metadata
    int64_t size = backend->file_size(path);
    time_t mtime = backend->modification_time(path);
    mode_t perms = backend->permissions(path);

    std::cout << "Size: " << size << " bytes" << std::endl;
    std::cout << "Modified: " << std::ctime(&mtime);
    std::cout << "Permissions: " << std::oct << perms << std::endl;
  }

  backend->unmount();
}
----

=== Seeking in Files

[source,cpp]
----
auto handle = backend->open("/mnt/app/data.bin", O_RDONLY);
if (handle) {
  // Seek to end to get size
  off_t size = handle->seek(0, SEEK_END);

  // Seek back to beginning
  handle->seek(0, SEEK_SET);

  // Seek to middle
  handle->seek(size / 2, SEEK_SET);

  // Read from middle
  char buffer[256];
  handle->read(buffer, sizeof(buffer));
}
----

=== Concurrent Access

The backend uses [`std::shared_mutex`](../../src/backends/zip_backend.cpp:60) for thread-safe access:

* **Read operations**: Multiple threads can read simultaneously
* **Write operations**: N/A (read-only backend)
* **Mount/unmount**: Exclusive access required

== Thread Safety

The backend implements comprehensive thread safety:

=== Read Operations

Multiple threads can safely:

* Open different files simultaneously (with serialization workaround for libzip)
* Read from different [`FileHandle`](../../include/tebako/fs/file_handle.h) instances
* List directories concurrently
* Query file metadata

=== Limitations

* File opening is serialized due to libzip internal limitations
* Mounting/unmounting requires exclusive access
* Each thread should use separate [`FileHandle`](../../include/tebako/fs/file_handle.h) instances

== Known Limitations

=== ZIP Format Limitations

==== No Native Seek Support

ZIP format stores compressed data sequentially. Seeking requires:

1. Closing the current file handle
2. Reopening the file from the beginning
3. Reading and discarding data until target position

This adds 5-20 ms overhead per seek operation.

==== POSIX Permissions Not Reliably Stored

ZIP format has limited support for UNIX permissions:

* Most ZIP archives don't store POSIX permission bits
* Windows-created ZIPs typically lack permission data
* Backend uses defaults: 0644 for files, 0755 for directories

==== Read-Only Access

The backend does not support:

* Writing new files
* Modifying existing files
* Deleting files
* Creating directories

This is by design for the Tebako use case.

=== libzip Limitations

==== Concurrent File Opening

libzip has internal limitations with concurrent [`zip_fopen_index()`](../../src/backends/zip_backend.cpp:200) calls:

* Race conditions may occur with simultaneous opens
* Workaround: Serialize file opening operations
* Reading after opening is fully thread-safe

==== Memory Usage

* Each open file allocates decompression buffers
* Large numbers of open files may consume significant memory
* Recommendation: Limit concurrent open files to reasonable count (< 100)

== Implementation Details

=== Path Handling

The backend normalizes paths before libzip operations:

[source,cpp]
----
std::string ZipBackend::normalize_path(const std::string& path) const {
  // Remove mount point prefix
  std::string rel_path = strip_mount_point(path);

  // Remove leading slash
  if (!rel_path.empty() && rel_path[0] == '/') {
    rel_path = rel_path.substr(1);
  }

  // Empty path means root
  if (rel_path.empty() || rel_path == "/") {
    return "";
  }

  return rel_path;
}
----

=== Error Handling

All operations return appropriate error indicators:

* [`open()`](../../include/tebako/fs/filesystem.h:89): Returns `nullptr` on failure
* [`mount()`](../../include/tebako/fs/filesystem.h:82): Returns `false` on failure
* [`file_size()`](../../include/tebako/fs/filesystem.h:132): Returns `-1` on error
* [`list_directory()`](../../include/tebako/fs/filesystem.h:118): Returns `nullptr` on failure

Errors are logged but not thrown, maintaining C compatibility.

=== Resource Management

The backend uses RAII for resource management:

* ZIP handle closed in destructor
* Open files tracked and closed on unmount
* Mutex released automatically via guard
* No manual memory management required
